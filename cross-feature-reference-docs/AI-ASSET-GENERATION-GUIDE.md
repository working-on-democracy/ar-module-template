# AI asset generation & stylizing guide

<!-- overview -->
## Introduction

Instead of modelling every object by hand, a 3D model can be generated by
an AI service from a photo, a drawing or a sentence of text. What comes
back is usually detailed, smooth and realistic — often more than a phone
needs, and not always the look a project wants.

The template has two small command-line tools for this. The first sends a
picture or a text to a generation service and saves the model it returns.
The second turns any model into a deliberately simple, hand-crafted
looking object: few, clearly visible flat faces, a coarse texture whose
individual pixels you can see, and stronger colours. Both run on your own
computer, without Blender or any other desktop program, and both keep the
untouched original so you can try again with different settings.

The stylizing tool also packs the result for the phone right away, and a
third command chains everything: give it a picture, and it ends with a
new, ready-to-use object in the scene — always the same steps, with the
glitter and shadow settings already right. This guide explains both tools, the order to use them in, and
what to watch out for — including that generation services cost money,
and that what you upload to them is not private.

<!-- /overview -->

## About this guide

Not tied to one feature — these tools produce `.glb` files for any scene.
Read this before generating a model with an external service, before
reducing a model's triangle count or texture size, and before debugging a
stylized model that looks smeared instead of pixelated.

## 1. The pipeline

### One command: picture → entity — `scripts/image-to-entity.ts`

```
npm run image-to-entity -- generated-assets/foto.jpg --name figur --height 0.96
```

1. **generate** — `sloyd-generate.ts image … --faces 20000 --texture 2k`
   → `generated-assets/<name>.glb`. Asks before spending credits
   (`--yes` skips). **Skipped when that file exists**, so re-running
   never pays twice; `--glb <file>` starts from any model instead.
2. **stylize** — `stylize-glb.ts` with the defaults picked on a phone
   (`--faces 1500` → ~3000 with seams kept, `--texture 128`,
   `--saturation 1.3`), compressed → `src/assets/<name>.glb`.
3. **measure** — model height → `grainScale` for ~2400 grain cells over
   it (0.12 units → 20000, the value tuned on a phone).
4. **insert** — into `src/ArModule.vue`, inside a marked block at the end
   of `#scene-root` (created on first use). Re-running with the same name
   replaces that entity; everything else in the file stays untouched:

```html
<!-- image-to-entity: generated entities — managed by `npm run image-to-entity`, edit freely -->
<!-- figur -->
<a-entity id="figur-wrapper" position="0 0 0" scale="8.024 8.024 8.024">
  <a-entity id="figur" gltf-model="#figur"
      shadow="cast: true; receive: true"
      shadow-side="back"
      grain-shimmer="filter: nearest; grain: 0.15; grainScale: 20000"
      gesture-control="drag: false"></a-entity>
</a-entity>
<!-- /figur -->
<!-- /image-to-entity -->
```

Options pass through: `--faces`, `--texture`, `--saturation`, `--grain`
(0 = none), `--height` (wrapper scale, so the model's own scale stays 1
for pinch-scale), `--position`, `--sloyd-faces`, `--sloyd-texture`,
`--replace` (re-stylize an existing name), `--no-gestures`, `--no-insert`
(print only). `gesture-control="drag: false"` (two-finger rotate,
pinch-scale; [GESTURES-FEATURE-GUIDE.md](../guides/GESTURES-FEATURE-GUIDE.md))
sits on the model, the `--height` scale on a wrapper — pinch-scale reads
its base scale once at init. Two-finger gestures are scene-wide: all
generated entities turn and scale together.
Placement is deliberately not decided: the entity sits at the
`#scene-root` origin, on the floor. On `feature_template` itself don't
commit the inserted entity — `ArModule.vue` stays generic there
(AGENTS.md §5); the command is meant for project forks.

### The single steps

```
npm run sloyd -- image foto.png                → generated-assets/foto.glb     (raw, local, gitignored)
npm run stylize -- generated-assets/foto.glb   → src/assets/foto.glb           (stylized + compressed, ships)
                                                 uncompressed-assets/foto.glb  (stylized, uncompressed original)
```

Each step keeps its input untouched, so any step can be rerun with
different settings.

- **Raw downloads never go into `src/assets/`.** Every file there is
  listed in the manifest, shipped and preloaded by the host — a 10 MB
  generated original would be downloaded by every visitor even if the
  scene only uses its stylized copy. `generated-assets/` is gitignored and
  never scanned by the build.
- **`stylize` compresses by default** — with the very code
  `compress-assets` uses (`scripts/glb-compression.ts`: `gltfpack -c -kn
  -km`, mesh names reattached, textures to *lossless* WebP, no resizing;
  output verified byte-identical). It puts the uncompressed stylized model
  where `compress-assets` keeps its pristine originals, so a later
  `compress-assets` run works from it, never from the compressed file
  ([ASSET-COMPRESSION-GUIDE.md](ASSET-COMPRESSION-GUIDE.md)).
  `--no-compress` writes the uncompressed model to `src/assets/` instead,
  for compressing later with other settings. A textured 3000-triangle
  figurine: 323 KB → 115 KB, no visible difference on a phone.
- `stylize` refuses already meshopt-compressed or quantized input: the
  geometry would be quantized a second time.
- **Re-stylizing a model already in `src/assets/`** needs `--replace`: it
  overwrites both the `src/assets/` file and its `uncompressed-assets/`
  copy (with `--no-compress` it deletes that copy, so `compress-assets`
  doesn't keep compressing the old version).
- `stylize` works on any `.glb`, not only generated ones — e.g. a pristine
  original from `uncompressed-assets/`.

## 2. Generating with Sloyd — `scripts/sloyd-generate.ts`

```
npm run sloyd -- text "a weathered wooden chair" --faces 5000 --texture 1k
npm run sloyd -- image chair.png --faces 5000 --texture 1k --name chair
npm run sloyd -- multi --front f.png --back b.png --left l.png
npm run sloyd -- resume <jobId> --name chair
```

| Option | text | image | multi |
|---|---|---|---|
| `--faces` (target, 0 = Sloyd decides, max 500000) | ✓ | ✓ | ✓ |
| `--texture` 128/256/512/1k/2k/4k/auto/none | ✓ | ✓ | on/off only (PBR) |
| `--topology` auto/quads/triangles | ✓ | ✓ | fixed by Sloyd |
| `--tpose` | ✓ | | |

- **Credentials:** `SLOYD_CLIENT_ID` (starts with `sok_live_`) and
  `SLOYD_CLIENT_SECRET` in `.env.local` at the repo root (gitignored). The
  key's display name in Sloyd's dashboard isn't needed. Never use a
  `VITE_` prefix and never reference them from `src/` — Vite would inline
  them into the publicly hosted bundle.
- **Credits:** every job is prepaid. The script prints an estimate from
  Sloyd's price list and asks before sending (`--yes` skips). Roughly:
  image + texture ≈ 20, text + texture ≈ 25, multi-image ≈ 30.
- **Job log:** Sloyd has no "list my jobs" endpoint. Every `jobId` is
  appended to `.sloyd-jobs.jsonl` (gitignored); `resume` fetches a job
  whose polling was interrupted. Files in `generated-assets/` are never
  overwritten — each one cost credits.
- **Concurrency:** while Sloyd's API is in test, at most 5 jobs per key may
  run at once (429 otherwise).
- **No text instructions with an image.** `image-to-3d` takes no prompt.
  Sloyd's `image-edit` (edit the picture with a prompt first) and
  `retexture` (re-paint a finished model from a prompt) endpoints exist but
  aren't wired into the script yet.
- **Generate moderately detailed, stylize locally.** `--faces 5000
  --texture 1k` gives `stylize` enough detail to average from; trying
  different low-poly targets locally costs nothing, regenerating does.

## 3. Privacy: uploads and results are public

Sloyd stores uploaded images and finished models at public, unauthenticated
Google Cloud Storage URLs keyed by the job id
(`storage.googleapis.com/ai-services-quality/jobs/<jobId>.glb|.webp`).
Anyone who has or guesses the id can download them, and Sloyd runs AI
captioning on uploads. Don't upload photos of people or anything
confidential.

## 4. Stylizing — `scripts/stylize-glb.ts`

```
npm run stylize -- generated-assets/chair.glb --faces 800 --texture 64 --saturation 1.3
npm run stylize -- generated-assets/chair.glb --faces 400 --out /tmp/try.glb   # try without touching src/assets/
```

| Option | Default | Effect |
|---|---|---|
| `--faces` | 1000 | target triangle count |
| `--texture` | 64 | longest texture side in pixels |
| `--saturation` | 1.3 | 1 = unchanged |
| `--smooth` | off | keep soft normals instead of hard facets |
| `--permissive` | off | also simplify across texture seams (see step 2) |
| `--keep-maps` | off | keep normal/metal-roughness/occlusion maps |
| `--no-compress` | off | write uncompressed to `src/assets/` (see §1) |
| `--name`, `--replace`, `--out` | | output naming, see §1; `--out` writes just that one file |

What it does, in order:

1. **Merge** parts that share a material (`flatten` + `join`), so the
   triangle budget goes where it's least visible. Simplified one by one,
   every small part would lose the same share and tiny parts (rivets,
   buttons) would vanish. Skipped for animated/skinned models, whose node
   structure has to survive — there small parts lose the most, and the
   script says so.
2. **Simplify** with meshoptimizer to the target, keeping UV seams in
   place. On the fragmented UV layouts of AI models that stops early —
   a textured Sloyd figurine bottomed out at ~3000 of a 1500 target — but
   the texture stays clean on every face. `--permissive` sets
   meshoptimizer's `Permissive` flag so edges collapse across seams too:
   the target is reached, but texels get stretched along collapsed seams
   into streak and ring patterns that are clearly visible on colourful
   textures (and invisible on near-uniform ones, where it's the better
   choice). Going lower than the seams allow, with a clean texture, would
   need a new UV layout and re-baking the texture — not done by this tool.
3. **Hard edges:** every triangle gets its own vertices and face normal.
4. **Materials:** normal/metal-roughness/occlusion maps dropped, metallic 0,
   roughness 1 (metal without an environment map renders dark in the
   host); base-colour factors and float vertex colours saturated.
5. **Textures:** colour textures shrunk with averaging (colours stay
   right) and saturated, stored as PNG.
6. **Samplers:** `minFilter`/`magFilter` = `NEAREST`. That is what makes
   the pixels visible — not the texture size. No mipmaps are built, so from
   a distance the surface flickers/sparkles as texels jump with every
   movement. three.js reads glTF samplers on load, so no component is
   needed, and the compression step (`gltfpack -c`) keeps them (verified).

### Combining with grain-shimmer

`grain-shimmer="filter: nearest"` sets the same sampling at runtime and
adds shader grain on top ([GRAIN-SHIMMER-FEATURE-GUIDE.md](../guides/GRAIN-SHIMMER-FEATURE-GUIDE.md)).
With a stylized model, `filter` is already baked in; use the component for
the grain. It only *shimmers* when one grain cell is smaller than a screen
pixel; bigger cells read as static dark specks (found on a phone,
2026-10-06). `grainScale` counts cells per model unit, so work it out from
the size on screen: a Sloyd figurine 0.12 units tall, shown 0.96 m tall at
2.5 m, covers roughly 400–800 px — `grainScale: 1500` (180 cells) gave
specks, ≥ 8000 is needed for 1–2 cells per pixel.

**Standard for stylized models** (picked on a phone, 2026-10-06, from
0.1–0.4 at 20000): `grain-shimmer="filter: nearest; grain: 0.15; grainScale: 20000"`
— a fine, subtle glitter. Scale `grainScale` with the model's size in its
own units (≈ 2400 grain cells over its height). The component's own
defaults (0.35 / 300) are unchanged. Works on the compressed output too
(see the grain guide §4 on quantized meshes).

### Shadow acne

Self-shadowing stylized models (`shadow="receive: true"`) show shadow acne
— fine striped/moiré self-shadow — on nearly every facet with `shadowBias`
alone (checked headless by diffing against `receive: false`). Two cures
removed it: `normalBias` ~0.02 on the light (not exposed by A-Frame's
`light`, and it changes everything that light shadows) and
`shadow-side="back"` on the model (only back faces go into the shadow
map). `image-to-entity` sets the latter — it belongs to the model, not the
scene.

Both need a shadow map fine enough for the model. The template start
scene's light used to cover ±80 m with `shadowRadius: 12` (≈ 8 cm per
shadow-map texel) — on a 1 m figure back-face shadow still blurred onto
thin parts. Since 2026-10-06 it covers ±5 m around `#lightTarget` (now at
the origin), `shadowRadius: 2`, `shadowBias: -0.0005` (≈ 5 mm per texel);
with `shadow-side="back"` that renders clean (checked headless). For a
scene larger than 10 × 10 m widen the shadow camera, accepting softer
shadows.

## 5. Incompatibilities, risks & troubleshooting

- **Pixels look smeared after compression:** the model was (re)compressed
  with `compress-assets` using lossy WebP or resizing. `stylize` itself
  always compresses losslessly; in `compress-assets` choose lossless and no
  resizing — at 64–128 px there's nothing to save anyway.
- **Streaks or ring patterns in the texture:** made with `--permissive`;
  leave it off for colourful textures.
- **Texture looks like colour noise instead of pixel art:** AI texture
  atlases are fragmented into many small islands; at very low resolution
  neighbouring islands bleed into each other at seams. Try a larger
  `--texture` (128).
- **Thin, plate-like models** (sheets, blades, leaves) suffer most from a
  low `--faces` — they turn spiky. Raise the target.
- **More triangles than asked for:** texture seams stop the reduction
  (step 2) — accept it, or `--permissive` for near-uniform textures.
- **Fewer triangles than asked for:** many separate small parts in an
  animated model, see step 1.
- **Name-dependent features** (e.g. `mesh-render-order` by mesh name) won't
  find their meshes after stylizing: merging renames and flattens nodes.
  Stylize such models with care or not at all.
- **Draco-compressed input** isn't supported (no decoder installed).
- Headless rendering of a model to compare before/after: stock A-Frame
  1.3.0 (same three r137 as the host) renders in headless Chromium with
  `--enable-unsafe-swiftshader`; the vendored 8frame build doesn't start a
  scene without an XR session.
